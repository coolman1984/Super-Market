# النسخة السحابية (Cloudflare) — نسخ احتياطي ومزامنة

**الحالة:** منفذة ومختبرة آليًا (Worker حقيقي بمحاكي D1 محلي). لم تُجرَّب على جهاز المحل الحقيقي ولا مع هاتف بعد. اختيارية بالكامل: محل لا يوصلها لا يتغير فيه شيء سوى جدولين فارغين (ترحيل ٨).

## الفكرة في سطرين

جهاز المحل يظل **المصدر الوحيد للحقيقة**؛ يرفع كل تغيير إلى السحابة تلقائيًا (بأمان وبترتيب)، فتصير السحابة **نسخة احتياطية حيّة** ومصدر قراءة للهواتف. الأجهزة الأخرى لا تكتب صفوفًا؛ ترسل **أوامر** يشغّلها جهاز المحل بصلاحياته وقواعده المعتادة ثم يرد بالقبول أو الرفض.

```
جهاز المحل (SQLite)  ──signed push──▶  Worker + D1  ◀──pull / commands──  هاتف / جهاز آخر
        ▲                                   │
        └───────────  ack / نتيجة الأوامر ───┘
```

## ما يُرفع وما لا يُرفع

| يُرفع | لا يُرفع أبدًا |
|---|---|
| كل جداول البيانات (أصناف، دفعات، حركات، مبيعات، مدفوعات، يومية، تدقيق، إعدادات المحل، مستخدمون بلا كلمات سر) | كلمات السر وملحها (`pw_hash`, `pw_salt`) |
| | الجلسات `sessions`، طابور الطباعة `outbox`، الأرصدة المشتقة `stock_balances` (تُعاد بالمشغّل)، حالة المزامنة المحلية |
| | **بيانات التدريب** (التفعيل يرفض غير المحل الحقيقي) |

> بيانات العملاء (الأسماء والهواتف والديون) تُرفع كما هي إلى حساب كلاودفلير الخاص بالمالك. قرار المالك: قبول ذلك أو استبعاد جدول `customers` (انظر «قرارات مفتوحة»).

## قاعدة التعارض (لماذا لا تضيع بيانات)

* **صف واحد = آخر نسخة تفوز.** مفتاح الصف (المحل، الجدول، rowid). لكل تغيير رقم نسخة `v` متزايد يصدره جهاز المحل (`sync_changes.seq`)، والسحابة ترفض أي رقم أقدم أو مكرر (يمنع رجوع صف قديم عند إعادة الإرسال).
* الصفوف المرحَّلة **غير قابلة للتعديل أصلًا** (قيود قاعدة البيانات)، فلا تعارض عليها. الأعمدة القليلة القابلة للتغيير (حالة دفعة، قفل وردية…) تُرسل من جديد وآخرها يفوز.
* **الحذف** يصل كشاهد قبر (`deleted=1`) فلا يعود الصف بعد حذفه.
* **كاتب واحد**: لا يوجد خلاف بين جهازين يكتبان نفس الصف لأن الهواتف لا تكتب صفوفًا. الكتابة من الهاتف (أوامر) تمر على جهاز المحل بمفتاح منع تكرار (`key`)؛ نفس المفتاح مرتين = نفس النتيجة بلا تنفيذ ثانٍ.
* انقطاع الإنترنت: التغييرات تبقى في `sync_changes` وتُرسل عند عودته (انتظار يتضاعف حتى ١٠ دقائق). لا يتوقف البيع أبدًا بسبب السحابة.

## الأمان

* **توقيع كل طلب** HMAC-SHA256 على (الطريقة، المسار والاستعلام، الوقت، nonce، بصمة الجسم، المحل، الجهاز). نافذة ±٣٠٠ ثانية، وnonce لمرة واحدة لغير GET، فلا إعادة تشغيل للطلب ولا تعديل لجسمه أو مساره.
* **سر كل جهاز** = HMAC(`MASTER_KEY`, محل|جهاز) — لا يُخزن في السحابة. يحصل عليه الجهاز مرة واحدة بـ**رمز اقتران** لمرة واحدة (صالح ١٥ دقيقة، مخزن مجزأً، محاولات خاطئة محدودة).
* عزل تام بين المحلات (كل استعلام مقيَّد بمعرّف المحل) · أدوار: `shop` (يرفع ويشغّل الأوامر) و`mobile` (يقرأ ويرسل أوامر) · إلغاء جهاز فوري (`admin revoke`) · حدود معدل · لا تسريب لتفاصيل الأخطاء.
* الخدمة **تفشل مغلقة** إن غاب `MASTER_KEY` أو `ADMIN_KEY`.
* لا مفاتيح في المستودع: `sync.json` (سر هذا الجهاز) و`cloud/.admin-key` في `.gitignore`، والمفتاحان يُخزنان مشفرين في كلاودفلير فقط ولا يُطبعان.

## التركيب (مرة واحدة، يفعله المالك أو المساعد الفني)

1. **نشر الخدمة:** `cloud\deploy.bat` (ويندوز) أو `node cloud/deploy.mjs`. ينشئ قاعدة D1 باسم `super-market-sync` ويطبّق `schema.sql` وينشر الـWorker وينشئ `MASTER_KEY` و`ADMIN_KEY` **مرة واحدة** (لا يستبدلهما لاحقًا) ويحفظ `ADMIN_KEY` في `cloud/.admin-key` على هذا الجهاز فقط. أو من GitHub: Actions → Cloud copy → Run workflow → deploy (يحتاج أسرار المستودع المذكورة في الملف).
2. **تسجيل المحل:** `python tools/syncctl.py admin new-store --url <العنوان> --name "اسم المحل"` ثم `admin pairing --store <المعرّف> --role shop` فيظهر رمز لمرة واحدة.
3. **توصيل جهاز المحل:** `cloud-join.bat` (يسأل العنوان والمعرّف والرمز) أو `python tools/syncctl.py join ...`، ثم أعد تشغيل البرنامج. يرفع نسخة كاملة أولى ثم كل تغيير.
4. **المتابعة:** `python tools/syncctl.py status` — `complete: true` تعني أن عدد صفوف كل جدول متطابق هنا وفي السحابة ولا شيء ينتظر.

للهواتف لاحقًا: `admin pairing --role mobile` لكل هاتف، والهاتف يقرأ بـ`GET /v1/pull` ويرسل أوامر بـ`POST /v1/commands`. **لا توجد أوامر مسجَّلة بعد** سوى `ping`؛ تُضاف في `CloudSync.handlers` أمرًا أمرًا، كل واحد يمر على خدمات البرنامج (صلاحيات، منع تكرار، تدقيق).

## الاستعادة بعد ضياع الجهاز (اختبرت آليًا)

```
python tools/syncctl.py admin pairing --url <العنوان> --store <المعرّف> --role shop     (على أي جهاز عنده مفتاح المدير)
python tools/syncctl.py restore --url <العنوان> --store <المعرّف> --code <الرمز> مجلد-جديد-فارغ
```

* يملأ **مجلدًا جديدًا فارغًا فقط** ولا يمس شيئًا آخر، ويرفض نسخة سحابية أحدث من البرنامج أو فارغة.
* يبني القاعدة بنفس مخطط النسخة ثم يرقّيها بالمسار المعتاد (مع نسخة قبل الترقية)، ويفحص المفاتيح الأجنبية، ويشغّل `reconcile()` (مطابقة الأرصدة والمدفوعات والحسابات) ويعرض النتيجة.
* **كلمات السر غير موجودة في السحابة**: بعد الاستعادة شغّل `owner-recovery.bat` لكلمة سر جديدة للمالك، وأعد ضبط كلمات سر الباقين من الإعدادات.
* الأرقام التسلسلية تكمل من حيث توقفت ورقم النسخة يبدأ فوق آخر رقم في السحابة فلا يتعارض شيء.
* بعدها: ألغِ جهاز المحل القديم `admin revoke` حتى لا يرفع جهازان على نفس المحل.

## الحدود والتكلفة

* الخطة المجانية لـD1: ١٠٠ ألف عملية كتابة/يوم، وكل صف مرفوع كتابة واحدة. محل صغير بضع مئات من الصفوف في اليوم فيكفي بسهولة؛ النسخة الأولى الكبيرة قد تمتد على أيام إن كانت القاعدة ضخمة (الرفع يستكمل من حيث وقف). تنظيف يومي تلقائي للـnonce وسجلات الاقتران القديمة (cron).
* ملفات (صور، PDF) غير مدعومة؛ ستحتاج R2 وقد يتطلب بطاقة دفع. غير مفعّلة.
* واجهة داخل البرنامج لحالة المزامنة غير مكتوبة بعد؛ الحالة من `syncctl status` وملف `server.log`.

## قرارات مفتوحة للمالك

١. رفع بيانات العملاء (أسماء، هواتف، ديون) إلى حسابه، أم استبعاد `customers`.
٢. هل يكفي النطاق المجاني أم الخطة المدفوعة (٥ دولار شهريًا) لاحقًا.
٣. هل يكتب الهاتف أي شيء (بيع، جرد…) أم قراءة وتقارير فقط في البداية.
٤. من يحتفظ بـ`ADMIN_KEY` (نسخة آمنة خارج الجهاز) — لا يمكن إظهاره ثانية.
٥. توصيل جهاز المحل الحقيقي (لم يُوصَّل شيء حقيقي حتى الآن).
